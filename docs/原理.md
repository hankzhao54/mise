# 原理说明

配合 `server/engine/` 里的代码阅读。每一节标了对应的文件和函数。
每条规则在 `server/test.js` 里都有一段手算核对，跑 `npm test` 能看到它们逐条通过 —— 那个文件本身就是一份可执行的原理说明。

哪些规则来自 Apicbase 的文档、哪些是我补的，见 `Apicbase功能对照.md`。

## 0. 一句话概括

这类系统只有两个核心：

- **配方是一棵树**：菜品 → 半成品 → 原料。成本、过敏原、用料需求、扣库存，都是在这棵树上做递归。
- **库存是一本流水账**：任何进出都追加一行，现存量 = 所有行相加。收货、销售、生产、调拨、盘点，只是写入这本账的不同原因。

其余所有功能 —— 订货建议、生产计划、内部订货、批次追溯、毛利报告 —— 都是在这两样东西上做查询或写入。

## 1. 数据模型（db.js）

```
settings (全局默认值)

suppliers ── packages ── ingredients ─┐
                │                      ├─ recipe_lines ─ recipes ─ menu_items ─ menus
        package_prices                 │        (行指向原料，或指向另一个配方)
                                       │
outlets ─┬─ stock_moves ── lot_moves ── lots ── lot_links (批次父子关系)
         ├─ par_levels (最低量 / par / 储位)
         ├─ stock_counts ─ count_subs ─ count_entries      (确认后 → count_lines)
         ├─ purchase_orders ─ po_lines ─→ packages
         ├─ internal_orders ─ internal_order_lines         (门店 → 中央厨房)
         ├─ production_plans ─ production_tasks ─→ recipes
         ├─ tasks ─ task_logs        ccps (全局)
         └─ pos_items ─ sales ─→ recipes
```

几个关键设计：

- **原料不带价格**。价格在包装上，因为同一种面粉可以有两个供应商、两种规格、两个价格。原料只定义基础单位（g / ml / 个），所有数量最终都换算到基础单位。
- **半成品和菜品是同一张表**（`kind`）。半成品再分「可入库」和「现做」（`stockable`），这个开关决定了扣库存时拆到哪一层（见第 4 节）。
- **很多字段允许为空，空 = 沿用上一级**：配方行的损耗 → 原料的损耗 → 全局默认；配方的税率、目标毛利率 → 全局默认；供应商的审批限额 → 全局默认。
- **库存品 = (item_type, item_id)**：原料和可入库的半成品都能入库。
- **主数据是全局的，业务数据是门店的**：配方、原料、菜单属于整个库；库存、订单、盘点、销售、任务都挂在某个门店上。

## 2. 单位换算（core.js · toBase）

每个单位有一个量纲和一个系数：`kg = (质量, 1000)`、`l = (体积, 1000)`。同量纲按系数换算，不同量纲直接报错。

## 3. 配方成本（core.js · recipeCost / pricing）

### 食材成本

对每一行：

```
损耗率   = 配方行上填的 ?? 原料上填的 ?? 全局默认        (子配方行：行上填的 ?? 0)
毛用量   = 净用量 × (1 + 损耗率)                         白菜 1500 g、损耗 20% → 1800 g
行成本   = 毛用量 × 单位成本
```

单位成本：

- 原料：`包装价格 ÷ 包装含量`。用哪个包装由设置决定 —— 最便宜的（默认），或最近一次订的。
- 子配方：**递归**算出它整批的成本，再 `÷ 产出量`。

### 人工成本与 prime cost

```
本配方人工 = (备料分钟 × 备料时薪 + 烹饪分钟 × 烹饪时薪 + 装盘分钟 × 装盘时薪) ÷ 60
整批人工   = 本配方人工 + Σ 子配方行 (毛用量 × 子配方每单位人工)
prime cost = 食材成本 + 人工成本
```

只算主动工时：炖着不用人看的时间不算。三个时薪都设为 0 就等于不计人工。

### 售价、毛利、目标（只有菜品有）

```
去税售价   = 含税售价 ÷ (1 + 税率)
利润       = 去税售价 − prime cost
毛利率     = 利润 ÷ 去税售价
食材成本率 = 食材成本 ÷ 去税售价

目标 prime cost = 去税售价 × (1 − 目标毛利率)                  价格不能涨 → 成本要压到这
目标含税售价    = prime cost ÷ (1 − 目标毛利率) × (1 + 税率)    成本不能降 → 价格要定到这
```

### 两个细节

- **循环引用**：递归时带着「当前路径」，再次遇到自己就报错；保存配方时先算一遍，出错则整个保存回滚。
- **成本从不存库**，每次现算。所以改一个包装价格、一个时薪、一个默认损耗，所有相关配方（隔几层都算）立刻变。

菜单（套餐）的成本就是各道一份相加，再套同一个 `pricing` 函数。

## 4. 配方展开（core.js · explode）

「做 / 卖 N 份这个配方，要从库存里扣什么？」

```
对配方的每一行：
    是原料            → 记下 毛用量 × 倍数
    是可入库的半成品   → 记下 毛用量 × 倍数   (到此为止：它有库存，扣它自己)
    是现做的半成品     → 递归进去，继续拆
```

为什么可入库的不往下拆：高汤是中央厨房提前做好、入了库的，猪骨在生产那一步已经扣过了，再拆就重复扣。
为什么现做的要拆：蘸料没有库存，不拆的话它用掉的酱油就永远不会被扣。

这个函数被五个地方共用：销售扣库存、生产领料、报废菜品、物料清单 (BoM)、需求预测。

## 5. 库存台账与批次（stock.js · addMove）

### 台账

`stock_moves` 只追加、不修改。`qty` 为正是入库，为负是出库。

| reason | 方向 | 谁写入 |
| --- | --- | --- |
| opening | + | 期初 |
| receive | + | 采购收货 |
| receive_internal | + | 内部订货收货 |
| production_in / production_out | + / − | 生产入库 / 领料 |
| transfer_in / transfer_out | + / − | 调拨（成对出现） |
| shipped_out | − | 内部订货发货 |
| sale | − | 销售按配方扣减 |
| waste | − | 报损 |
| count_adjust | ± | 盘点确认 |

库存允许为负。这是有意的：负数说明账实不符（货没收就用了、配方用量写少了），是需要被看见的信号。

### 批次（FEFO）

每条流水写入时同步批次：

```
入库：新建一个批次 (批号、效期、来源)。如果之前库存是负的，先补上欠的，剩下的才是这个批次的余量。
出库：按「先到期先出」逐个批次扣 —— 有效期的按效期从早到晚，没效期的排最后。
      每扣一个批次，记一行 lot_moves (哪条流水动了哪个批次、动了多少)。
```

恒等式：库存不为负时，`现存量 = Σ 流水 = Σ 批次余量`。

### 批次之间的父子关系（lot_links）

- 生产：领料动到的所有批次 → 成为产出批次的「父」。
- 调拨、内部订货：目的地新建同批号、同效期的批次，源批次是它的「父」。

**追溯**（`trace`）就是沿着这张关系图走：往上走到没有父的批次（原料的收货批次，带供应商），往下走到没有子的批次，并汇总每个批次的去向（哪几天卖了多少、报损多少、发走多少）。

## 6. 盘点（stock.js · createCount / confirmCount）

```
一次盘点 = 若干分盘 (几个人同时盘不同区域)
某品项的实盘数 = 所有分盘里它的数量之和
确认时：调整量 = 实盘 − 账面  → 写一条 count_adjust
没盘的品项：不动
```

「没盘」和「盘成 0」是两回事，这是最容易出错的地方：前者保持原库存，后者清零。
确认后账面等于实盘；那条调整流水本身就是「差异」，后面的报表直接读它。

## 7. 采购（procurement.js）

### 订货建议的两种算法

**补到 Par**（`parSuggestions`）：

```
可用量 = 现存 + 在途
如果 可用量 < 最低量：需要 = Par − 可用量
```

**需求预测**（`forecastSuggestions`）：

```
对未来 N 天的每一天：
    取同一个星期几的历史销量 (上周同日，或近 4 周同日的平均)
乘以缩放比例 → 得到每道菜的预测份数
按配方展开 (第 4 节) → 每样东西的预测用量
减去现存、减去在途 (两个都可以关) → 需要
```

两种算法得出「需要」之后走同一段代码（`buildSuggestions`）：

- 原料 → 选订货包装（最近订过的优先，否则最便宜的），数量**向上取整到整包**，按供应商分组。
- 可入库的半成品 → 普通门店：向中央厨房下内部订单；中央厨房自己：不订货，去排生产。

「在途」包括已下单未到货的外部订单和未收到的内部订单。没有它，货在路上的这段时间里系统会重复建议同一样东西。

### 订单状态机

```
in_progress ──提交──┬─→ sent ──收货──→ partial ──收货──→ delivered
                    │                     └────────────────↑ (一次收完直接到这)
                    └─超限额→ waiting_approval ─批准→ sent
                                    ├─拒绝(必须给原因)→ rejected ─重新提交→ …
                                    └─撤回→ in_progress
```

**审批判定**（`approvalCheck`）：这家店今天已发给这个供应商的金额 + 本单 > 限额。只有已发送的订单计入「今天已发」，所以它是一道提醒关卡，不是硬性上限。

### 收货（receivePO）

每行：全到 / 部分 / 没到。可以分多次收，订单保持 `partial` 直到收齐或手工关闭。

- 实付单价和订单价不同，且勾了「更新价格」→ 回写包装价格 + 写一行价格历史 → 所有配方成本自动变。
- 不勾「更新库存」→ 只记到货数量和金额，不写流水（货已经被盘点数进去了）。
- 入库时生成批次，带上供应商。

**发票核对**：`差额 = 发票金额 − 实收货值`。

### 内部订货

```
门店下单 (incoming) → 厨房拣货，可少拣 (picked) → 发货 (shipped) → 门店收货 (received)
                                                    ↑ 扣厨房库存      ↑ 加门店库存，批次镜像过来
```

发货和收货之间，货「在路上」：厨房已经没有了，门店还没到，但计入门店的在途量。
把所有新订单按配方汇总（`incomingDemand`）就是中央厨房今天的生产需求。

## 8. 生产计划（production.js）

```
草稿 draft ──激活──→ 进行中 active ──所有任务完成后──→ 已完成 done
任务:  todo ──开始(计时)──→ doing ──完成──→ done
```

- **带出子配方**（`subRecipeNeeds`）：做 400 只饺子要 6 kg 馅，馅是可入库的子配方 → 提示把馅也排进计划（库存够就不用）。
- **计划的物料清单**：各任务展开后相加，再**减去本计划自己会产出的半成品**（馅是这个计划里做的，就不算缺料）。
- **完成计划**（`finishPlan`）：对每个可入库配方的任务

```
按【计划量】领料            (理论投入)
按【实际产出】入库
入库单位成本 = 投入成本 ÷ 实际产出      计划 200 只、实际 180 只 → 每只贵 11%
效期 = 生产日 + 保质期天数；批号自动生成；领料用到的批次记为父批次
```

  先处理层级低的任务（被别人用的），这样上层任务领料时能领到刚入库的半成品。

## 9. 任务与 HACCP（haccp.js）

- **待办不存库**：每次按「任务定义 + 日期」现算（`isDue`），再和执行记录对上。这样改了任务频率，未来的待办自动跟着变，不需要批量生成或清理。
- 状态：有记录 = 已完成；没记录且日期已过 = 逾期；否则待办。
- **异常判定**：温度检查读数超出 [下限, 上限]，或清单有没勾的项 → `ok = 0`，并且必须写处理措施才能保存。
- 报告 = 一段时间内应做、已做、逾期、异常的数量，加上每条异常的读数和处理措施。

## 10. 销售（sales.js）

```
POS 商品 (PLU) ──关联──→ 配方 ──每卖一份──→ 按配方展开扣库存 (理论消耗)
```

- 未关联的 PLU：只记营业额，`depleted = 0`。关联时把这些销售补扣一遍。
- **关联健康度** = 已关联营业额 ÷ 全部营业额。不到 100% 时，利润是虚高的（有收入没成本）。
- 销售看板：`利润 = 去税营业额 − prime cost`；平均毛利率只在已关联的营业额上算。

## 11. 报表（reports.js）

全部是对台账和销售表的查询，不存中间结果。

### 期间库存

```
期初 + 收货 + 生产入库 + 调入 + 盘盈
     − 销售 − 生产领料 − 调出 − 内部发货 − 报损 − 盘亏 = 期末
```

每一项都对应台账里的一类流水，所以等式一定成立。

### 毛利报告

```
理论成本   = 销售按配方消耗的货值              (严格按配方做，应该用掉这么多)
净差异     = 盘盈 − 盘亏
实际成本   = 理论成本 + 报损 − 净差异
成本率     = 成本 ÷ 净营业额
```

理论和实际之间的差距，就是「配方算出来该赚的」和「实际赚到的」之差。
它由两部分组成：登记了的报损，和没人解释得了的盘点差异。后者的常见来源：出品份量超标、损耗没登记、配方用量写少了、收货短少没核对。

### 菜单工程矩阵

Kasavana & Smith 四象限法（行业通用方法）：

```
销量门槛 = (总销量 ÷ 菜品数) × 70%
毛利门槛 = 总毛利 ÷ 总销量
```

| | 毛利高 | 毛利低 |
| --- | --- | --- |
| **卖得好** | 明星：保持 | 耕马：小幅提价或降成本 |
| **卖得差** | 谜题：加强推荐 | 瘦狗：考虑下架 |

## 12. 几个贯穿全局的做法

- **事务**：一次业务动作涉及的所有写入（比如完成生产 = 若干条领料 + 入库 + 批次 + 任务状态）放在一个事务里，要么全成功要么全回滚。
- **请求上下文**：每个 HTTP 请求有自己的上下文（`AsyncLocalStorage`），里面放当前事务和一份「目录」缓存（设置、原料、包装、配方、门店）。配方成本是在目录上同步算的，所以一个请求里算几百次成本也只查一次库；写了主数据就 `refresh()` 重新读。
- **时间**：统一用本机时区的时间字符串，「某一天」的含义和营业日一致。
- **金额**：报表里的金额按当前单位成本折算。真实系统会保留每条流水当时的成本（`stock_moves.unit_cost` 已经存了，只是报表没用它）。

## 13. 数据库（db.js）

- 同一套 SQL 跑在两种 Postgres 上：线上是 Supabase（`DATABASE_URL`，`pg` 连接池），本地和测试是内嵌的 PGlite。
- 所有表建在 `mise` schema 里；每条连接拿到后先 `SET search_path`，所以要用 Supabase 的 **Session pooler**（连接在会话期间不换人）。
- 代码里写 `?` 占位符，执行前转成 `$1 $2…`；`?1` 这样带编号的可以重复引用同一个参数。
- 表结构只增不改：每次启动跑一遍 `CREATE TABLE IF NOT EXISTS`。
- 清空业务数据用 `TRUNCATE … RESTART IDENTITY`，但门店编号**不**重新计数：账号上按编号记着能看哪些门店，旧编号不能落到新门店头上。

## 14. 账号与权限（auth.js · server.js）

- **密码**：`scrypt` 加随机盐，存成 `scrypt$盐$哈希`；比对用定长比较 (`timingSafeEqual`)。同一 IP + 用户名 15 分钟内错 8 次就暂时锁住。
- **会话**：登录时生成 32 字节随机令牌放进 HttpOnly Cookie，库里只存它的 SHA-256。数据库泄露也拿不到能用的令牌。改密码、停用账号会删掉此人的所有会话。
- **权限检查都在服务端**，按顺序：
  1. 没登录 → 401。
  2. 请求里出现的门店（查询参数 `outlet`、请求体 `outlet_id` / `from_outlet`）必须在自己的范围内。
  3. 按 id 操作的单据（订单、内部订单、计划、盘点、任务、POS 商品）先查它属于哪个门店；内部订单下单方和供货方都算。
  4. 主数据的写操作要「改主数据」权限；审批 / 拒绝订单要「审批」权限；账号、门店、设置、清空数据只有管理员。
- **操作记录**：请求成功结束（状态码 < 400）后写一条，内容里的 password 字段替换成 `***`。
- **第一个管理员**：库里一个账号都没有时，用环境变量建；之后账号都在网页里管理。
